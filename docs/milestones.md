## マイルストーン 1：一本のトラックを最後まで通す

依頼 → 実行 → 承認 → 結果 → 仕上げを、一本のトラックで最後まで通す。

60個の完了条件の照合状況は [M1 受入条件の照合表](m1-acceptance.md) に記録する。個別の実装・試験だけで、M1全体を完了とは扱わない。

M1は 2026-11-05 に全受入条件を満たし、同日のユーザー指示どおり `417c665` でcommitした。

### 範囲

#### 本物にするもの

- 入力：テキストだけ（声は検証項目 ⑨ の後）。入力欄 → 帯のチップ → 置く。文字が入っている間は、右端に送信ボタン（↑）を出し、その ▾ に New track（⌘⇧↵）を置く（設計書「3.2 領域ごとの役割」の入力欄の形と文脈）。
- 置き場所：Glimmer を呼ばず、規則の段だけで置く。選んでいるトラック → 最後に話しかけたトラック → どちらも無ければ fork（設計書「9.3 分類（発話 → 編集操作）」の置き方は二段の一段目）。Glimmer の置き直しは、提出までの順の 2 で足す。ただし、送るのは Local の Glimmer の MLX のサーバーが、モデルを読み込んだ状態のときだけだ。読み込み中と、無いか落ちたときは送らず、帯に一行を出す（設計書「9.3 分類（発話 → 編集操作）」）。送る前に、最小の判定（操作と宛先を Local の `/decide` で読む）を通す。作る順の 4 で入れる（2026-11-03 のレビュー）。規則だけで送る開発用の切り替えは、足場の最初の数日だけ使い、完了の条件には使わない。判定の残り（置き方の二段の細部・期限・カード）は、提出までの順の 2 で足す。
- 点線のクリップ：走っているトラックへの境目待ちの言葉を、そのレーンの先に点線で描く（after this turn）。選んで ⌫ で切れる（cut）。
- プロジェクト：フォルダ一つのプロジェクトを、設定で与える。作成ダイアログ（板 0b）は後に回す。
- セッションの名前と slug：slug は `s-<yyyymmdd-hhmm>` だ。セッションを始めたときに決まり、変わらない（設計書「5. プロジェクト・セッション・git」のセッションの名前とブランチ）。名前は、最初の言葉の先頭 30 字にする。Glimmer が来たら、Editor が付け直す。
- ホスト：stdio の子プロセスを、トラックごとに一つ立てる（一本目はトラックが一本なので、ホストも一つ）。フラグ・許可リストの 8 個・渡す環境は、設計書「15. アーキテクチャ」の起動規定のとおりだ。走らせるのは、Intercat が持つ Muse Code の写しだ。インストール先の本体を APFS の複製で写して作る。写しの SHA-256・版・initialize の fingerprint の三つが合わなければ、走らせない（設計書 15 節の Muse Code の写し、検証項目 ㊸）。PATH はログインシェル（`$SHELL -lic`）から取って保存する（research/verify の E2）。approvalMode は常に promptUnmatched だ。
- ホスト専用の設定ファイル：デーモンが作り、その場所を `XDG_CONFIG_HOME` で渡す（設計書 15 節のホストの起動規定）。profile は `intercat-worker` で、`:ask-me` を継承し、秘密ファイルの deny を足す。既定の deny は `**/.env`、`**/.env.*`、`**/.envrc`、`**/*.pem`、`**/*.key`、`**/.netrc` だ。`.env.*` からは、例の名前（`.env.example`・`.env.sample`・`.env.template`・`.env.dist`）を除く。4つの例示名から接頭辞ごとの deny を生成し、それ以外の任意の `.env.*` 名を拒否する（検証項目 ㉝）。同じ一覧を、初期コミットの除外と開始元の検査にも使う。プロジェクトの Muse hook は、全部のホストで既定で止める。trust を付けずに起動し、AGENTS.md の指示は適用範囲を保ってターンに添える（検証項目 ㊽、2026-11-04）。capacity・道具の許可リスト・Contributor mode・モデルも、このファイルに書き、`-c` とフラグには書かない（第七回の F2）。利用者の settings は変えない。session/start では permissionProfile を省き、返事の profileId が `intercat-worker` でなければ走らせない。
- ホストの準備：セッションを作ったときに、持ち主の無いホストを一つ立てる。worktree と session/start まで済ませて待たせ、最初に言葉を受けたトラックに渡す。起動から userMessage までは、中央値 985 ms だった（第五回の A12）。こうしておけば、ホストの起動を待たない。最初の言葉が届くまでには、判定の待ちと保存が足される（下の完了の条件 1）。
- worktree と ref：ワーカーの worktree は detached HEAD で作る。トラックの先頭は、隠し ref `refs/intercat/<slug>/tracks/A` に記録する。ブランチ `intercat/<slug>` を持つのは、統合 worktree だけだ（設計書「19. worktree」の worktree の ref）。統合 worktree は、セッションとリポジトリの組ごとに一つだ。slug の重なりは、リポジトリの ref でも確かめる。
- 依存：worktree を作るときに、デーモンが sandbox-exec の中で入れる。プロファイルは、Check とは別だ（設計書「19. worktree」の依存の共有）。ダミーのリポジトリに依存が無ければ、この段は空で通る。統合の作業場所では、トラックを載せるたびに、manifest・lockfile・導入の設定のどれかが変わっていれば、lockfile を変えない導入（`npm ci`）で準備し直す。Check の直前は、変わっていなくても準備し直す。導入は、既定では秘密ファイルを読めない。失敗は env-failed で、Check は走らせない（設計書「13.3 Commit の手順」の手順 5）。
- デーモン：Rust で書く（設計書「15. アーキテクチャ」のセッションデーモン）。Node で書いて後から移す道は持たない。開発機に Rust のツールチェーン（rustup）が無ければ、作る順の 1 の前に入れる。MSP のクライアントは自前で、設計書 15 節の「Intercat が使うメソッド」の表の全部を持つ。公式の Rust の SDK（`muse-code-sdk` 1.4.14）は、クライアントには使わない。使うメソッドの一部を公開していないからだ（検証項目 ㉜。2026-11-01 に確かめた）。公開していないのは、fork・steer・interrupt・listPending・usage/read・skill/list などだ。UI が使うのが一部でも、デーモンは全部を持つ。
- Editor のループ：状態の遷移は一つのループで行い、待ちのある仕事（子プロセス・git・Check・依存の導入・ファイル・SQLite）はループの外で行う。ホストの stdout は常に読み続ける。イベントログは一本の書き手が書く。外へ送る命令は、二つの経路に分ける。新規の実行は書いてから送り、書けなければ送らない。「書いた」とは、実行の意図のトランザクションを commit したことだ。設定は `synchronous=FULL` と `fullfsync=ON` で、macOS では fsync だけでは電源断に耐えないからだ。質問への回答（userInput/answer）も、書いてから送る。停止（interrupt・unqueue・承認の abort・質問の中断・組への信号・ホストの終了）は、ログを待たずに送る。承認の拒否と、質問への回答・取り消し・説明は、ワーカーを続けさせるので、記録してから送る（設計書「17. Editor ハーネスの内部」の命令の表）。新規の実行の書き終わりは、イベントとしてループに返す。ループは送る直前に、決めたときと同じ条件（送れる条件の四つ・保留の全部・version・取り消し）を確かめる。保留が理由なら言葉を待ちに戻し、版の変更か取り消しなら superseded と書いて捨てる。条件は、命令の種類で分ける。送れる条件の四つはターンの開始にだけ当てる。Allow once と Run it under Intercat は stopping と log のときだけ拒む。確定済みの ref の更新は、log を除く保留に関わらず進める（設計書「17. Editor ハーネスの内部」のループの表）。
- 送る条件：turn/start は、四つが揃ったときだけ送る。四つ目は、答えを待つ質問がそのトラックに残っていないことだ。前の返答の「Waiting for you:」の行は規則で読み、遅れて届いた質問も数える（設計書「9.9 ワーカー出力の読み取り」の質問の関門）。残りの三つは、走っている turnId と開始の予約（starting）が無いこと、前のターンの終わりを確かめたこと、チェックポイントの保存が終わったことだ。予約は送ると決めた時点で立て、queued なら unqueue の結果まで保つ。予約の間の Stop は記録し、started が返ったらすぐ turn/interrupt を送る。走っている間の答えは送信待ちの言葉で、質問と結ぶ（Question.replyUtteranceId）。止めを外すのは返答を送ったときだけで、Take back と送信の失敗では未回答に戻す。返答は四つ目を問わず、ほかの質問を待たずに質問の順に送る。版（Question.rev）が違えば orphaned にする。表示の状態では決めない（承認待ちの stopped には送らない）。ifBusy は送らず、返りの disposition が queued なら、すぐ turn/unqueue で取り戻す。再接続と起動の後は、走っているターンと並んだ入力（session/read の queuedInputs）を作り直すまで送らない（設計書「9.4 走っているトラックへの言葉」、検証項目 ㊵）。
- 描画：最初から PixiJS（GPU）で描く（設計書 15 節の描画）。実機のトラックは 1 本でも、合成データで性能の門を通す。
- 舞台のキー操作：↑ ↓ で全トラックを一本ずつ選ぶ。先が画面の外なら舞台をスクロールし、選んだ行は仮想化で外さない。1–9 は近道として残す（設計書「3.4 タイムラインの描き方」のアクセシビリティ）。領域は ⌃Tab / ⌃⇧Tab で巡る（設計書「3.2 領域ごとの役割」）。アクセシビリティは、最小の鏡を入れる。role は `grid` で、行（トラック）の名前と状態だけを持つ。選んだ行は、画面の外へ出ても鏡から外さない。クリップのセル・住所・読み上げの規則は、マイルストーン 11 で足す。
- intercat-report：
  - ホスト専用の `<XDG_CONFIG_HOME>/muse/skills/intercat-report/` に置く。worktree と利用者のグローバル設定には置かない。
  - skill パートで渡し、依頼文は `arguments` に入れる。
  - 同じ形の指示を、依頼文の末尾にも入れる（保険。設計書「17. Editor ハーネスの内部」）。
  - 答えを待つ質問は、最後に「Waiting for you: …」の一行で書かせる。この行は規則で読む。
- タイムライン：一歩（モデルの一回の生成と、それに続くツール呼び出しの束）ごとにクリップを作る。言葉は、その userMessage の item で landed にする（設計書「16. データモデル」のクリップ化のルール）。再生ヘッドとクリップのバーは、実時間で進む。ターンの後も inProgress のまま残る bash の item からは、shell のクリップを作る（止める操作は後に回す）。
- 承認：
  - 承認のカードは、対象のパス・操作・戻せるかどうかを省略せず、折り返す。長いパスは break-all で折る。4 行を超えたらカードの中でスクロールし、末尾が隠れている間は Allow once を灰にする（副文「scroll to the end to allow」）。details ▾ は、生の要求（コマンドの全文・cwd・当たった規則）を開く（設計書「3.1 全体の配置」の横の配分、17 節の核が止めたときのカードの答え）。
  - ワーカーの承認要求は、すべて核が受ける（promptUnmatched）。核は、規則に当たらなければすぐに once で許可を返し、当たれば要求を保留にしてカードに出す。サンドボックスの外で走らせる要求は、ルールの一つ目として、命令の中身に依らずカードに出す（設計書 17 節のポリシー核）。照合には approvalId と requirementId を使う。
  - ポリシー核には、ルールの五種のうち四種から、次の六つの行だけを入れる（設計書 17 節）。
    - ルールの一つ目（サンドボックスの外で走らせる要求）の一行。
    - コマンドのパターンの三行：削除、`git push --force`、`git push`。削除の行には、作業ツリーの変更を捨てるコマンドも入れる。`git checkout -- .`・`git restore`・`git reset --hard`・`git clean -f`・`git stash drop` だ。削除は、対象がチェックポイントに入らないもの（worktree の外か ignore の対象）だけを止める。止めない削除では、デーモンが許可を返す前に worktree の写しを取る。写しが取れなければ、カードにする（設計書 17 節の削除の前の写し）。`--force` は、履歴を書き換えるから止める。ただの `git push` は、ワーカーが push しないから止める。
    - 通信先の一行：許可リストの外の宛先への接続を止める。既定のリストは localhost・127.0.0.1・::1、プロジェクトの git remote、パッケージの registry だ。
    - 対象パスの一行：保護された場所への書き込み（fileAccess の要求で protectedWrite: true のもの）をカードにする。`.muse/`・`.agents/skills/`・Git のメタデータへの書き込みが、これで止まる。
  - Effect の kind は、削除が delete、`git push` と `--force` が push、許可リストの外への接続が send（target は host:port）だ。
  - 設定 Stops の二択（Irreversible only / Every approval）を入れる。Every approval は、完了の条件 6b の試験に使う。
  - カードの答えは、固定の二つ「Allow once / Don’t run it」にする。どちらも、保留中の要求への答えだ。Allow once は once の許可を返し、保留していた同じ命令が走る（設計書 17 節の核が止めたときのカードの答え）。
- 止める：選んだトラックに ⌘.（今すぐ。turn/interrupt）と ⇧⌘.（走っているターンの後。境目待ちの言葉と点線は送らない）。走っているバーの右端の ■ と、トラック見出しの ⋯ にも、同じ二つを置く（設計書「3.2 領域ごとの役割」の走っているトラックを止める）。状態の行の左の端には、どれかが走っている間は常に「■ Stop all turns」を出す。その右に、選んでいるトラックが走っている間（承認待ちを含む）、文字のボタン「■ Stop A」を出す。読み上げの名前は「Stop all turns, 2 running」と「Stop Worker A」だ。
- 結果：
  - 報告の四部（1 行目に何が変わったかと差分の要約、変えたことの箇条書き、テストの結果、次の一手）が、ログに出る（設計書 17 節のワーカーの完了報告）。変えたことの各項目には、理由を一句添える。
  - ターンが終わるたびに、チェックポイント（隠し ref）を作る（設計書「12.4 チェックポイント」。分岐点がターンの切れ目にしか置けないので、単位もターン）。写しは、worktree の実 index の写しから始める。実 index は `.git/worktrees/<名前>/index` にあり、`git rev-parse --git-path index` で引く。リポジトリの `.git/index` を写すと、元のチェックアウトの index を写してしまう。Editor は、その SHA を報告の 1 行目に付ける。次のターンは、チェックポイントの保存が完了してから送る。シェルが残っている間に取ったものには印を付ける（設計書「12.4 チェックポイント」）。write-tree の前に、トラックを作った木に無い秘密の型のパスを、一時 index から除く。照らすのは Intercat の一覧だけで、リポジトリの ignore の規則は使わない（設計書 17 節の核に見えないもの）。
- Effect：ルールの行に当たって止めた呼び出しが Allow once で走ったら、その行の kind で Effect を一行記録する（設計書「16. データモデル」）。Every approval で止めただけの呼び出しは、Effect にしない。見え方は三つだ。クリップの ⇗、Commit シートの一行、報告の最後の Editor の一行。離席から戻ったときの数は、離席の扱いと一緒に後で作る。
- 仕上げ：設計書「13.3 Commit の手順」の道を、トラックが一つでも通す。
  - シートを開いた時点で、基点（トラックの base）・今回のチェックポイント・統合先の元の SHA を固定する（設計書「13.3 Commit の手順」の手順 2）。統合の仕事はセッション×フォルダに一つで、各窓のシートはその状態を購読する。Refresh は、走っている Check と導入を取り消し、止まったと確かめてから始める。非同期の結果は、始めたときの jobId・rev・treeSha が今と合うときだけ取り込む。Check の結果は、木と検査の設定（Checks・Check environment・Check network・Outbound hosts）のハッシュの組に結び付ける。仕事は自分の状態（IntegrationJob.status）と版（rev）を持ち、Track.status とは別にする。各窓は、確認した版（reviewedRev）を、描いた版と分けて持つ。ほかの理由で版が進んだら、確認済みを失効させ、理由と Review の帯を出す（「Changed in another window · Review」の形）。Commit は reviewedRev と対象の木の SHA の組を送り、違えば「The sheet changed · review again」で確定しない。シートは舞台だけを覆い、机（カード・帯・入力欄・状態の行）は生きたままにする。シートを開いている間に終わったターンは今回に入れず、「1 turn finished since you opened this · Refresh」の一行を出す。
  - 順は次のとおりだ。載せるのは、基点から今回のチェックポイントまでの差分だ。gix の木のマージで、作業ツリーに触れずに 3-way で当てる（merge driver は動かさない）。作業場所は、統合先の元から `file://` で作る浅い clone（depth 1）で、元のオブジェクト DB と履歴には届かない。clone には、checkout で使われる設定（改行と filter と属性。グローバルの設定を含む）を写す。LFS の置き場所は、clone の専用の場所だ（設計書「13.3 Commit の手順」の手順 5）。
    1. 結果の木を、`read-tree --reset -u` で作業場所に展開する。トラックの間では、木に無いファイルを消さない。Check の直前に、`git clean -ffdx` で木に無いものを全部消し（ignore の対象も）、依存の準備を無条件でやり直す。共有するのは中身で決まる取得物だけで、どの仕事からも読むだけだ。実行できる生成物は、仕事ごとに置く（設計書「13.3 Commit の手順」の手順 8）。その後に、統合の木を read-tree した一時 index に `add -A` して write-tree した木が、統合の木と一致することを確かめる。空の index から始めると、force-add した追跡ファイルが抜けて食い違う。それを `git commit` で、一時 ref `refs/intercat/<slug>/staging` の候補のコミットにする（2026-11-03 のレビュー）。メッセージは、シートに出す最終の文だ。候補は一度だけ作り、メッセージが変わったときだけ作り直す。commit-tree は使わない。hook（pre-commit・commit-msg）を、sandbox-exec の中で通すためだ。hook は、木に無いものだけ（`.git/hooks` の中身と、生成された補助ファイル）を、候補を作る `git commit` の直前に元と同じ相対位置へ写す（clone には来ないから）。追跡済みの hook は、統合の木にあるものを使う。入口は写した hook の名前だけを照らし、欠けていれば止める。拒否は Check が赤のときと同じに扱い（hook-rejected）、出力を見せる。木と `.git` の外にある hook は写さず、カードで止める。文は「Hooks need files outside the repo · Commit without hooks / Discard」だ。二つは対等で、白にしない（設計書「13.3 Commit の手順」の手順 5、検証項目 ㊻）。`git commit` の前に、統合先の元の木に無い秘密の型のパスを、作業場所の index から除く。除いたパスは、シートに「left out: config/.env.staging (secret file)」と出す。
    2. Check（`npm test`）を、作業場所で走らせる。Check の後にも一致を確かめる。追跡ファイルが変わっていれば、成功を無効にして check-mutated にする（カード「Check changed 2 tracked files · include them / treat as failure」）。作業場所で作ったコミットのオブジェクトだけを、gix で元のリポジトリに取り込む。
    3. Commit を押すと、確認した候補のコミットのまま確定へ進む。`git commit` は走らせ直さない。人がシートでメッセージを直したら、候補を作り直し、Check をやり直す（2026-11-03 のレビュー）。受理したら、統合の仕事を committing にし、rev・木・メッセージを固定する。その間は Refresh・二つ目の Commit・Discard を拒み、どの窓にも「Committing… · wait」を出す。届いた merge クリップの結果と直しの取り込みは待たせる。成功は done、失敗は open に戻す（設計書「13.3 Commit の手順」の手順 13）。
    4. ブランチを先に、トラックの記録を後に、期待値を照らして一つずつ進める（gix）。ブランチ `intercat/<slug>` の期待値は、統合先の元の SHA だ。`refs/intercat/<slug>/integrated/A` と `base/A` は、今回のチェックポイントに進める。シートを開いた後にブランチの先頭が進んでいれば、何も上書きせずに Refresh を出す。
    5. 進める前に、操作（opId と、各 ref の old / new）をイベントログに書き、終わったら done を書く。起動時に、done の無い操作をやり直す。ref が old なら new へ進め、new なら飛ばし、どちらでもなければカードで止める。セッションのブランチは、new が今の先頭の祖先でも済んだと見なす。それ以外で先頭が進んでいたら、統合の仕事を open に戻し、Check と確認済みの版を失効させる。カードの文は、設計書「18. 失敗と上限」の正常に終わった印にある（the branch moved）。
    6. ボタンを灰にするのは、Check が通っていない間、ディスクと木が一致しない間（Check の前と後）、版が進んで Review を押していない間だけだ。
  - シートのトラックの行は二段だ。上の段は「Included · up to A:3 · 3 clips · +41 −11」で、入る最後のクリップの住所を出す。下の段は「Not included · running now · thinking」だ。走っていないトラックは、Included の一段だけだ（設計書「13.3 Commit の手順」の手順 2）。
  - シートは、モーダルではない領域だ。役割は `region` で、Radix の Dialog は使わない。フォーカスを閉じ込めず、外側を押しても閉じない。Esc は、シートの中にフォーカスがあるときだけ閉じる。変換中・Monaco の検索や補完・文字の欄の中では閉じない。閉じたら、フォーカスは開いた元か入力欄へ戻る（設計書「13.3 Commit の手順」の手順 3）。本文はスクロールし、確定のボタンの列は下に固定する（設計書 3.1 の横の配分のシート）。
  - Check の結果は、検査した木に結び付ける。木が変われば、結果は無効になる。
  - Check と hook は、作業場所の上で、sandbox-exec のプロファイルの中で走らせる（設計書 17 節の OS の実行制限、検証項目 ㉖・㉟・㊱）。書き込みは作業場所とその仕事の一時ディレクトリだけにし、ネットワークは切る。読みは許可リストに限る（作業場所・その仕事の一時ディレクトリ・保存した PATH の各ディレクトリ・依存の共有キャッシュ・OS の領域）。元のリポジトリの `.git` は許さない。
  - 秘密ファイルは、どの worktree にも写さない。Check environment は、一本目では無し（既定）にする。設定で選べる形はM2で作成済み。Exportに渡さない条件はM8で確認する。
  - Intercat の git の操作は二種に分ける。管理の操作（ref の更新、オブジェクトの読み書き、一時の index からの木、merge-base）は、git を起動せずに gix で行う（検証項目 ㊱）。git の CLI は、worktree の操作とリポジトリのコードを動かし得る操作だけで、どれも sandbox-exec の中で走らせる。git の CLI が元のリポジトリに書くときは、同期の設定を付ける（macOS の既定は writeout-only。検証項目 V53）。付けるのは `-c core.fsync=objects,reference -c core.fsyncMethod=fsync` だ。
  - プロファイルは、設計書「17. Editor ハーネスの内部」の OS の実行制限の五つだ（git だけ・チェックポイント・起動を許す・Push・シェル）。書き込みは、その仕事の一時ディレクトリまでに限る。
  - Intercat が作るコミットは署名しない（`-c commit.gpgsign=false`。gix のコミットも署名なし）。
  - 手順 0（提案）、6〜7（衝突）、10〜11（担当）と、16 の合わせ方は要らない。
  - トレーラーには、名前と住所の両方を書く（`Intercat: <名前> · <slug>/A:3`）。設計書の例は `Intercat: Login hardening · s-20261031-1400/A:14` だ。
- 測る仕組み：介入の回数と遅れ、切った点線の数、誤って走った手の数を、イベントログから集計する（[設計引き継ぎの評価](design-handoff.md#評価)）。測る実験そのものは、提出までの順の 3 で行う。
- レンダラーの境界（設計書「15. アーキテクチャ」）：Markdown はサニタイズして描き、生の HTML は描かない。外部の画像は自動で取りに行かず、枠と load を出す。load とリンクは、開く前に URL の全文を見せる。CSP（connect-src 'none' など）と窓の設定は、最初から入れる（検証項目 ㊴）。
- イベントログ：すべての入出力を SQLite に書く。時刻は二つ書く。日時は epoch、経過はデーモンの単調時計（眠りも数える `mach_continuous_time`）だ（設計書「16. データモデル」の時刻）。アプリとデーモンを止めて立て直したとき、モデルもホストも呼ばずに、セッションを描き直せる。受けた生のフレームと、状態に反映する単位を分ける。状態は (museSessionId, itemId) ごとに、新しい revision で上書きする。resume の履歴は、新しい item として足さない（設計書「16. データモデル」の真実の源。第六回の R4）。item の本文は 1 MB までで、超えたら頭と末尾を残して truncated の印を付ける。受信が保存を超えても stdout は読み続け、列はホストごとに 8 MB までにする。まず表示用の delta を落とし、それでも溢れたら turn/interrupt とカード「output too fast to record」だ（設計書 17 節のループ、検証項目 ㊾）。
  - 書けないとき（SQLITE\_FULL・SQLITE\_IOERR・書き手が 2 秒応えない）は、dispatchHold に log を入れる。帯に「New work paused · can’t save to the log · disk is full · Stop still works」を出す。言葉は「not saved」で残す。
  - 書けなかった停止は、MSP の記録と組の生死から補い、unlogged の印を付ける。
  - 正常に終わった印：起動で「started (gen N)」、正常な終了で「clean (gen N)」を書く。次の起動で前の世代の clean が無ければ、何も自動で投入しない。帯には「Intercat stopped unexpectedly · 3 held」を出す。Commit の ref の更新は、ログから最後まで進める（設計書「18. 失敗と上限」の正常に終わった印）。
- 生きたプロセスの走査：ホストの環境に `INTERCAT_HOST=<nonce>` を入れる。印の環境変数と、worktree の中の cwd・開いたファイルの二つで走査する。ホスト自身は除き、印の無いプロセスには信号を送らない。組の外に出たものは、PID と開始時刻で照らして一つずつ止める（設計書「11.4 ワーカーが完了したとき」、検証項目 ㊺）。走査が読む環境変数は `INTERCAT_HOST` だけで、ほかは捨て、ログに書かない。
- ⌘Q の Stop everything：設計書「18. 失敗と上限」のホストの終了の四段を作る。一段目は、新しい仕事を始めない（dispatchHold に stopping）。二段目は、デーモンの仕事（Check・依存の導入）を取り消す。Commit の ref の更新だけは終わらせる。三段目はプロセスを止めることで、中身は手順 1〜3 だ。四段目は、次に立ち上げたときに何も自動で投入しないことだ。stdin を閉じ、5 秒で終わらなければ SIGTERM、さらに 5 秒で SIGKILL を送る。その後、記録した組を掃除する。終了の完了は、記録した組と、走査で見つかる印のあるプロセスが無いことだ。止められない組が残れば、完了と出さず、残った組を出す。
- Stop all turns：メニューバーの Agents に置く（⌥⌘.）。Stop everything の一段目と二段目に、全ターンの turn/interrupt を足し、アプリは終えない。ホストと記録した組は止めず、確認も出さない。帯に「Turns stopped · 2 processes still running · Resume · 3 held」を出す（数が 0 の部分は出さない）。stopping は Resume まで残す。Resume を押すと、stopping を外してから held の一覧を開く（Start all と項目ごとの Start）。Resume だけでは何も走らない（設計書「18. 失敗と上限」の全体の停止）。状態の行の左の端の「■ Stop all turns」は、走っている間は選択に依らず常に出す（Home でも）。位置も字も変えず、押せない時間も作らない（設計書 3.2 の走っているトラックを止める）。
- Stop all turns and processes…：同じメニューの、Stop all turns の下に置く。確認の窓を出し、既定の Stop を白にする。近道は付けない。中身は終了しない Stop everything で、ホストも閉じる。次の言葉で、ホストは約 1 秒で立ち直る（設計書「18. 失敗と上限」のターンとプロセスの停止）。
- 吹き出し：固定の文字列の二つだけを出す（設計書「4. キャラクター」の表）。
  - 初回：「Hi. I’m Intercat, the editor. You talk; I cut.」
  - Commit：「Committed. Push when you like.」

#### 一本目だけの扱い

設計書と違う形にするのは、次の三つだけだ。仮定と名前は、Glimmer の生成を呼ばないことから来る（判定は呼ぶ）。Reply は、範囲を小さくするためだ。

- 仮定：規則で置いても、仮定にしない。一本目は、Glimmer で判定していないだけだ。だから、Commit シートの仮定の行は空になる。
- カードの答え：「Allow once / Don’t run it」の固定の二つにし、Reply は出さない。Reply は Glimmer を通らない（拒否に文を feedback として添える。添えられないときだけ、先に止めてから訂正を送る。設計書 17 節）ので、作るのは易しい。一本目では、範囲を小さくするために出さない。
- 名前：最初の言葉の先頭 30 字にする。設計書では、Editor が付ける。

#### 後に回すもの（スタブか Off）

- Reviewer（Off）、Planner、Image、Push と PR、Branch from here、確認モード、Privacy gate、通知。
- キャラクターの動き（静止画の Idle だけ）と、Glimmer の台詞。
- 土台のファイル（`.git/info/exclude`、intercat-report）の写しと、Restore / Keep のカード（設計書 17 節の核に見えないもの）。秘密ファイルは写しではなく、deny で守る（M1 に入れる）。
- 5 分動きの無いホストを止める規則。
- Git の無いフォルダの初期コミットと、未コミットの変更の問い（マイルストーン 6）。ダミーのリポジトリは、未コミットの変更の無い状態から始める。
- ポリシー核の残りの行（対象パスの残り、見えない仕事を作るコマンド、DROP / ALTER・migrate などのコマンドのパターン、shell の段の POST などの字面の規則）。
- cap の auto（マイルストーン 7）。固定の cap（既定 4）と待ち行列は、提出の線に入れる（2026-11-03 のレビュー）。密度の三段、群レーン、ミニマップ（マイルストーン 7）。

### 試験の場

- ダミーのリポジトリ：Node のリポジトリで、ログイン関数と、テスト 2 本（`node --test`）を持つ。`npm test` が通る状態から始める。使っていない `src/unused.js` も置いておく（完了の条件 23）。`src/version.js` も置く（完了の条件 26）。`package.json` の prepare で `src/value.js` を `dist/` に写し、テストの一本が `dist/` を読む形にする（完了の条件 27）。ローカルの小さな依存 `vendor/tiny-dep`（`file:` で足せる形）も置く（完了の条件 24）。`.gitignore` に当たる `fixtures/` に、force-add した fixture を一つ置く（完了の条件 33）。
- remote は、手元の bare リポジトリ（`file://`）にする。Allow once で push が走っても、Mac の外へは出ない。
- 認証は、従量の API キー（Muse Code に保存したもの）を使う。従量では Contributor mode の設定の行が無く、保存値も無いので、ホスト専用の設定ファイルに `contributor_mode_enabled: false` を書く。モデル ID は、利用者の settings.json の model を写す。検証の環境は `muse-spark-1.3-contributor` だ（設計書「7. 認証と初回の準備」の Contributor mode）。
- 従量なので、Usage のリングは出ない。これはスタブではなく、設計どおりの動きだ。
- Privacy gate は Off なので、ダミーのリポジトリと依頼文には秘密を入れない。

### 完了の条件

ダミーのリポジトリで、次を一続きの操作で通す。

1. 「ログイン関数にリトライを足して、テストを走らせて。最後に `git push origin HEAD:refs/heads/try-a` を走らせて」と打つ。帯にチップが 0.1 秒以内に出て、トラック A が立つ。言葉が userMessage として届き、クリップが伸びる（ホストは、セッションを作ったときに立ててある）。届くまでの時間は、送ってからの待ちと推論の時間を分けて測る（2026-11-03 のレビュー）。条件の秒数は、実際のプロンプト・判定の列・保存を含めて測ってから決める。判定の中央値は 1.05 秒なので、ホストの準備だけでは 1 秒の根拠にならない。
2. 点線を一本切る：A が走っている間に「CHANGELOG にも一行足して」と打つ。言葉は規則で A に置かれ、A のレーンの先に点線のクリップ（after this turn）が出る。それを選んで ⌫ で切ると、点線が消え、言葉は送られない。A は止まらずに走り続ける。
3. ワーカーが push を試みると、承認要求の段で核が止めて、カード（Allow once / Don’t run it）が出る。A は stopped（理由は approval）になる。Don’t run it を押すと、push は走らず（`git ls-remote` で、bare の remote が変わっていないことを見せる）、A は push をせずに続きを終える。push の item/started が要求への答えより後に来ること（答える前に走っていないこと）も、ログで確かめる。
4. 完了：ログに報告の四部が揃って出る。変えたことの各項目に、理由の一句が付いている。1 行目の SHA は、そのターンのチェックポイントと一致する。レーンの末尾に ✓ が付く。
5. 続けて「もう一度 `git push origin HEAD:refs/heads/try-a` を走らせて」と話しかけると、A が続きを始め、またカードが出る。Allow once を押すと、保留していた同じ push が走り、bare の remote に try-a が届く。
   - 宛先を書いて頼むのは、ワーカーの worktree が detached HEAD だからだ（ただの `git push` は、今のブランチが無いので失敗する）。それに、「push して」とだけ言う文は、Glimmer が来ると command = push（アプリの Push）に読まれる（設計書「5. プロジェクト・セッション・git」）。この文なら、ワーカーの仕事として読まれる。
   - この push は Effect になる（kind は push、target は bare の remote）。push のクリップに ⇗ が付き、報告の最後に Editor の一行「Effects: pushed origin」が出る。
   - bare の remote は worktree の外にある。Muse のサンドボックスが push の書き込みを止めるか、要求がサンドボックスの外で走らせる形（require_escalated）で来るかは、検証項目 ⑪ と ㉕ 次第で、まだ確かめていない。完了の条件は、核のカードで止まり、Allow once の後に bare に届くことだ。
   - 要求の形と、サンドボックスが止めたかを、⑪ と ㉕ の結果として [research/verify](../research/verify/README.md) に記録する。
6. 許可前の副作用ゼロ：shell は実行の前に、通信は接続の前に、核が答える。6a と 6b に分けて確かめる。
   - 6a（shell）：ここまでのログの全ツール呼び出しで、shell の要求への核の答え（approval/decide）が、その item/started より先にある。核が答える前に始まった命令は、一つも無い（promptUnmatched で、核が全要求を見ている）。通信先の要求は、shell が始まった後、通信の時点で届く（検証項目 ㉕-4）。だから通信は、6b で別に確かめる。
   - 6b（通信）：手元で listen ポートを一つ立て、受けた接続をすべてログに書く（bare の remote の `../remote.git` は使わない）。設定 Stops を Every approval にして（通信先の要求もカードにする）、A に `curl http://127.0.0.1:<port>/` を走らせる。shell の要求には Allow once、通信先の要求（127.0.0.1:<port>）には Don’t run it で答える。curl は失敗し、listen ポートのログに接続が一つも残らない。
   - 6b で Every approval を使うのは、127.0.0.1 が許可リストの中にあり、Irreversible only では止まらないからだ。許可リストの外への接続が Irreversible only で止まることは、この試験では見ない。
   - 6b を終えたら、設定 Stops を Irreversible only に戻す。
7. Commit：
   - シートが開き、仮定の行は空のまま、Check（`npm test`。sandbox-exec のプロファイルの中）が緑になる。
   - シートに「Effects outside git · 1 · pushed origin <時刻> · not undone by branch or restore」の行が出る。ボタンは無い。
   - Commit を押すと、統合 worktree の `intercat/<slug>` に 1 コミットが載る。ワーカーの worktree はブランチを持たないので、fast-forward は git に拒まれない。
   - `git log` のトレーラーに `Intercat: <名前> · <slug>/A:<番号>` が入る。
8. 止める：A に、何歩かかかる依頼（「ログイン関数のテストを 5 本足して、一本ずつ走らせて」）を送る。走っている間に ⌘. を押すと、走っている一歩が cut で閉じ、A は done になる。終わり方は stopped-by-you で、見出しは灰の ■ と「stopped」になる（緑の ✓ ではない）。Editor のモデル（Glimmer）は動いていない（一本目は呼ばない）。止める操作はモデルを通らず、デーモンが直接 turn/interrupt を送るので、モデルが止まっていても中断できる。もう一度同じ依頼を送り、走っている間に「CHANGELOG にも一行足して」と打ってから ⇧⌘. を押す。A のターンは最後まで走り、その後、境目待ちの言葉は送られず「held · Start」で残る。⌘. は、押した時点で走っていたターンの turnId を明示して送る。
   - bash が走っている間に止めたとき、そのプロセスが残るかを、この試験のログで見る。残れば、shell のクリップになる。
9. kill -9 からの再接続：A に何歩かかかる依頼を送り、走っている間に A のホスト（`muse serve`）を kill -9 する。A は reconnecting になり、20 秒以内に戻る。戻る道は、新しいホストの session/resume（excludeItems）と approval/listPending だ。欠けた分は、記録した viewCursor から view/page で読む（設計書「18. 失敗と上限」の再接続の手順）。第五回の A4 では、約 1 秒で戻った。 2026-11-04 の実装検証では、承認待ちの実行中ホストを強制終了し、同じセッションへの自動再接続とチェックポイント保存まで 3,821 ms。開始の再送と承認命令は無し（`research/verify/reconnect-20261104/`）。
   - 途中のターンも戻る（userMessage と、完了していたツール）。走っていた bash は failed、保留中だった承認は rejected で閉じる（第五回の A4）。途中の一歩は failed で閉じ、古い承認のカードは無効にする（再表示も再承認もしない）。A は waiting か done になり、その言葉をもう一度送るかは、人が決める。
   - ターンの後に残ったシェルは、shell のクリップとして見える（検証項目 ⑱）。
10. 分岐の土台（検証項目 ⑧ の続き。UI の Branch from here は後）：A のあるターンのチェックポイント（turnId と SHA の一組）を使う。デーモンはそこから新しい worktree を作り、同じ turnId で session/fork する。分けた会話には、毎回 turn/start の `workspaceRoots` で新しい worktree を渡す。session/fork の workspaceRoot は無視されるからだ（第五回の A3）。新しい worktree の HEAD の木が ref の SHA の木と一致し、git status が空。分けた会話は、そのターンまでを持ち、新しい worktree のファイルを読む。
11. アプリとデーモンを両方止めて、立て直す。同じタイムラインが SQLite から描き直される。A は done なので、ホストは立て直さず、モデルも呼ばない。
12. ⌘Q → Stop everything：ホストが正常に終わり、ホストとその子孫が ps に残らない。
   - A に開発サーバーを立てさせ、A のホストを先に kill -9 してから Stop everything を押す。サーバーの HTTP が応答しなくなり、記録した組に生きたプロセスが残らない。正常な EOF の試験だけでは、この条件を満たさない。
13. 性能の門（検証項目 ㉓）：300 トラック × 300 クリップの合成データ（日本語の題を含む）で、全体図でも 60fps、フレームの JS は 2ms 以内。100 本のバーが同時に伸びても、60fps と 2ms 以内を保つ。
14. Rust の MSP クライアントが、research/verify の記録を偽のホストから再生したとき、TS SDK と同じ状態に復号する。比べるのは、セッションの局所ビュー、承認の照合、再送の判定と、送ったフレームだ。対象は、設計書 15 節の「Intercat が使うメソッド」の表の全部と、記録にある通知のすべて（検証項目 ㉔）。表には、userInput/engaged・clarify・interrupt と、承認の abort も入る。生のホストへの接続は、疎通の煙試験だけにする。
15. 同じターンの削除：A に「新しいファイルを作り、同じターンでそれを rm して」と頼む。rm は止まらずに走り、その前に取った写しの木から、ファイルを書き戻せる。`git checkout -- .` で変更を捨てた場合も、同じく戻せる。
16. 二度目の Commit：7 の後、A に続きの依頼を送り、終わってから二度目の Commit をする。二度目のコミットには続きの変更だけが載り、一度目の変更は二重に載らない。
17. シート中に終わったターン：A が走っている間に Commit のシートを開き、そのまま A のターンが終わるのを待つ。シートに「1 turn finished since you opened this · Refresh」が出て、押すまで今回の差分は変わらない。Refresh を押すと、差分と Check がやり直しになる。
18. ループの応答：遅い Check（`sleep 20` を含むテスト）を走らせている間に、承認要求に一つ答え、⌘. を押す。どちらも、Check の終わりを待たずに処理される。
    - 複数のトラックの形（提出の前倒し。下の「提出までの順（済み）」）：手で立てた三本のトラックで行う。A の仕事の Commit で遅い Check を走らせている間に、B の承認に答え、C を ⌘. で止める。どちらも、シートを開いたまま画面で行う（机のカードで答え、1–9 で C を選んで ⌘.）。どれも、ほかの待ちに詰まらずに処理される。
19. 保護された場所：A に「`.muse/hooks.json` を write_file で作って」と頼む。核がカードを出す。Don’t run it を押すと、ファイルはできない。
20. 秘密ファイル：ダミーのリポジトリの直下と `packages/app/` の下に、ダミーの `.env`（ignore の対象）と `.env.example`（追跡する）を置く。
   - A の worktree にも、統合 worktree にも、`.env` は無い。Check と同じ sandbox-exec のプロファイルで `cat` しても、元のチェックアウトの `.env` は読めない。
   - deny を確かめるため、A の worktree の同じ二か所に、ダミーの `.env` を直接置く。A に read_file で読ませると、どちらの `.env` も失敗し、`.env.example` は読める。
   - session/start の返事の profileId は `intercat-worker` だ。
21. Commit の途中の停止：Commit を押した直後にデーモンを kill -9 して、立て直す。ブランチと `integrated/A` は両方とも後にあり、イベントログの操作は done になる。途中で止まっていても、起動時に old から new へ進める。二度目の Commit で、同じ変更が二重に載らない。
22. ↑ ↓ の移動：13 の合成データで、↓ を押し続けて 300 本目まで選ぶ。選んだ行は毎回画面に出て、選択は途中で外れない。画面の外から来た行も、VoiceOver が名前と状態で読む。
23. 消したファイル：A に「`src/unused.js` を消して」と頼み、Commit する。統合 worktree のディスクにもそのファイルは無く、ディスクと木の一致の確かめが通る。
24. 依存を足す：A に「`vendor/tiny-dep` を依存に足して、ログイン関数で使って」と頼み、Commit する。統合 worktree でも依存が準備され、Check が通る。lockfile を package.json と食い違わせた回と、package.json だけを変えた回では、準備が走って `npm ci` が失敗し、統合の仕事が env-failed になる。Check は走らない。
25. 止める途中の仕事：遅い Check（`sleep 20` を含む）を走らせ、A の境目待ちの言葉を一つ置いたまま、⌘Q → Stop everything を押す。Check は取り消され、言葉は送られない。立ち上げ直すと、言葉は「held · Start」で残り、何も自動で走らない。
26. Check が追跡ファイルを変える：テストの一つが `src/version.js` を書き直す形にして Commit する。Check の後の一致に通らず、統合の仕事が check-mutated になる。include them を押すと、差分が A のコミットに入り、Check がやり直しになる。
27. 古い生成物：シートを開いて Check を緑にする。その後、A に `src/value.js` の値を変えさせる（dist を読むテストが落ちる値）。ターンが終わったら Refresh する。manifest は同じでも準備が走り直し、Check は赤になる（前の dist を読んで通らない）。
28. 表示側：A に、外部の画像を含む Markdown を返させる。画像の URL は、手元で listen するポートにする（6b と同じ道具）。台本には枠と load が出て、ポートに接続は来ない。load を押すと URL の全文が出て、確かめた後に一度だけ接続が来る。
29. 承認待ちの言葉：A が承認を待っている間に、「CHANGELOG にも一行足して」と打つ。言葉は帯で待ち、送られない。承認に答え、ターンが終わってチェックポイントが保存されてから送られる。開発用の切り替えで条件の確かめを外して送ると、disposition が queued になる。すぐ取り戻され、言葉は Take back できる（検証項目 ㊵）。
30. ログの障害：開発用の切り替えで、書き手に SQLITE\_FULL を返させる。帯に一行が出て、新しい言葉は「not saved」で残り、送られない。走っている A は ⌘. で止まる。書き手を 2 秒止める形でも同じだ。書けるようになると、止めた記録が unlogged の印で入る。書けない間にデーモンを kill -9 して立て直すと、何も自動で投入されない。書けない間に境目待ちの言葉を置いて ⇧⌘. を押し、A のターンが正常に終わってからデーモンを kill -9 する。立て直しても、言葉は送られない（前の世代の clean が無いため）。
31. Stop all turns：A が走り、境目待ちの言葉が一つある状態で、⌥⌘. を押す。A のターンは止まり、言葉は送られない。ホストは残り、A が立てた開発サーバーの組も残る。Resume を押しても、言葉は「held · Start」のままだ。状態の行の「■ Stop all turns」を押しても同じだ。完了した A を選んでいても押せる。
32. 写しの照合：写しの本体を書き換えると、三つの照合に通らず、ホストは立たない。
33. force-add の fixture：A に fixture と関係の無い変更を頼み、Commit する。Check の前と後の一致の確かめが通る。A が `git add -f` して、まだコミットしていないファイルも、チェックポイントに入り、Commit に載る。skip-worktree か assume-unchanged の印を付けたファイルの変更も、チェックポイントに入る。疎なチェックアウトの型の外のファイルは、消えずに HEAD の中身のまま残る。手で印を付けたファイルを消すと、削除が写る。
34. 組の外に出たプロセス：検証項目 ㊺ でサンドボックスが止めなければ、A に `start_new_session=True` で起こすサーバーを残させる。Stop everything の後、そのプロセスも残らない。
35. 答えを待つ返答：A に、二つの案のどちらにするかを聞き返させる依頼を送り、境目待ちの言葉を一つ置く。返答の最後に「Waiting for you:」の行があれば、言葉は送られず、質問のカードが出る。
36. hook を写す：元のリポジトリの `.git/hooks/pre-commit` を、必ず 1 で終わる形にして Commit する。統合の仕事は hook-rejected になり、行に hook の出力が出て、コミットは作られない。
37. 書き込み待ちの命令と Stop：開発用の切り替えで書き手を遅らせ、A への言葉を送る。書き終わる前に ⌥⌘. を押す。書き終わっても言葉は送られず、held の一覧に残る。
38. シートと承認：最小の窓（1040×760）で Commit シートを開いたまま、B の承認のカードにキーボードだけで答える。⌃Tab で机へ移り、答えた後に ⌃⇧Tab でシートへ戻る。変換中の Esc では、シートは閉じない。
39. 止めた hook：リポジトリの `.muse/hooks.json` に、決まったファイルに書くだけの PreLLMCall の hook を置く。ワーカーのターンを走らせても、そのファイルはできない（設計書 17 節の核に見えないもの、検証項目 ㊽）。
40. 確定中の排他：開発用の切り替えで、確定（ref の更新）を 5 秒止める。その間に別の窓で Refresh を押す。Refresh は拒まれ、両方の窓に「Committing… · wait」が出る。Commit が通ると、仕事は done になる。
41. Editor の保留：Local の Glimmer の MLX のサーバーを止めると、言葉は送られない。帯には「Editor unavailable · words wait · Stop still works」が出る。⌘. と承認の応答は通る。立て直してモデルを読み込む間は「Editor starting · words wait」で、読み込んだら待っていた言葉が送られる。モデルのファイルを壊すと、3 回の自動の立て直しの後に「Retry / Details」が出て、Details から「Download again」で戻せる。
42. デーモンの唯一性：デーモンを二つ起動しても、復旧するのは一つだけだ。二つ目は既存のデーモンに接続し、DB の復旧もホストの起動もしない。古いソケットが残っていても、ロックを取れた側が作り直す。
43. 遅い Check と Refresh：遅い Check の途中で、別の窓から Refresh を押す。走っていた Check は止まってから仕事がやり直され、古い結果は取り込まれない。
44. Stop の後の保留：A を ⌘. で止めた後に Reviewer の指摘が届いても、fix の点線は held のままで走らない。A に話すか、Start を押すと進む。
45. 承認の拒否：拒否は続けさせる応答として、記録してから送る。stopping の間と、ディスクが満ちてログに書けない間は送らず、カードに理由を出す。cap を 1 にし、A が承認待ちの間に B を頼む。A は待つ間も枠を持つ（検証項目 V52 まで）ので、B は列で待つ。A に Don’t run it を押すと A が続き、B は A の終わりまで待つ。
46. Git の永続化の順：統合の取り込みの途中でデーモンを落としても、操作ログの SHA のオブジェクトは、元のリポジトリにある。
47. 再送の重複：開発用の切り替えで、言葉を受理した直後に UI との接続を切る。窓は同じ操作 ID で送り直す。言葉は一つだけで、turn/start も一度だけだ（設計書 22 節の実行）。
48. ワーカーからの RPC：A のシェルから、デーモンのソケットへの接続を試す。繋がらないか、token が無いので切られる。A のホストの環境と、デーモンの引数に、token が無い（検証項目 V55）。
49. clone の symlinks：元に `core.symlinks=false` を置き、リンクを読む検査を用意する。元で失敗する検査は、clone でも失敗する。
50. 外への取得：A に、許可リストの外のホストを web_fetch させる。「A wants to fetch example.com · Allow for this session / Don’t」が出る。許すと、Effect にホストとメソッドだけが残り、query は残らない。
51. 仕事ごとの tmp：A の仕事から、B の仕事の一時ディレクトリを読み書きさせる。どちらも拒まれる。
52. 外の仕事の子孫：Check のテストコマンドに、子のプロセスを残して終わらせる。仕事は、子が止まったと確かめるまで終わらない。
53. HEAD の無いリポジトリ：git init だけをしたフォルダで始める。人の main は空のまま、セッションのブランチが親の無い starting point から始まる。Open PR は「no base branch yet」で灰だ。
54. 添付の除外：`.intercat/attachments/brief.txt` を `git add -f` し、`.gitignore` の否定のパターンも置く。チェックポイントにも Commit にも、添付は入らない。
55. 未解決の競合：人の checkout に merge の途中の競合を残して始める。「Your checkout has unresolved conflicts · resolve them first · Cancel」で止まる。
56. 止める道とログ：書き手に SQLITE\_FULL を返させたまま、窓の Stop を押す。RPC の入口で待たずに、turn/interrupt が届く（UI → RPC → MSP の全部の道）。
57. 組み込みのスキルの隔離：intercat-report がホスト専用のカタログにだけ出る。リポジトリに同名のスキルがあっても、そのファイルと index は変更されない。専用設定のスキルは worktree の外にあり、チェックポイントにも Commit にも入らない。
58. 非対応のリポジトリ：LFS を使うダミーのリポジトリで始める。「This repository uses Git LFS · not supported yet · Cancel」で止まり、セッションは作られない。filter と sparse checkout のリポジトリも、仕組みの名前を替えた同じカードで止まる（2026-11-03 のレビュー）。
59. 毎回変わる hook：pre-commit の hook がビルドの ID を書く形で Commit する。候補のコミットは一度だけ作られ、Commit は確定する。commit-msg の hook が文を足したら、シートには足した後の文が出る。シートでメッセージを直すと、候補を作り直し、Check をやり直す。
60. ワーカーの未解決の競合：A に merge の途中の競合を残させる。チェックポイントは作られ、シートに「A has unresolved conflicts in 2 files · Ask A to resolve」が出る。解くまで Commit は灰だ。

### マイルストーン 3：並列と計画

M2から移す残件（2026-11-07、2026-11-08に受入先を補足）：言葉のplan-onlyと計画の移動・依存変更・削除。Deleted plansの復元とUndo、Plannerのconflictsのカードも含む。各機能の実装と同じ段で接続する。計画を動かして走らせた後でも、M2で作ったTaken backの一覧から取り下げた言葉を戻せることも、ここで確認する。

- cap と待ち行列：走るワーカーのターンを 4 本に抑える固定の上限は、M1 で作った。残りは次のとおりだ。上限は設定 Parallel workers の数で、既定は 4 だ（auto はマイルストーン 7）。cap が数えるのは、走っているワーカーのターンだ。枠は開始の予約で取り、ターンの終わりが分かった時点で一度だけ返す。返す道は、turn/completed・turn/unqueued・steered の返り・開始のエラー・送る前の取り消し・Run の lost だ。人を待つターンも、検証項目 V52 で確かめるまでは枠を持ったままにする。返してよいと分かったら、待つ間は枠を返す。続けさせる応答（Allow once・承認の拒否・質問への回答と取り消しと説明）は、その Run が枠を持っていれば使い、無ければ取ってから送る。カードは「approved · waiting for a slot · Cancel」「declined · waiting for a slot」で、列では先にする。すぐ送るのは、Stop・承認の abort・質問の中断だけだ。期限は、カードに残りの時間で出す（先に検証項目 V52）。列では人の言葉を計画より先にし、すでにホストがあるトラックの言葉のチップは「queued · 2nd」だ。Planner と Reviewer のターンは、ワーカーの cap とは別の上限（既定 2）で数え、429 の判断にも入れる。待機中のホストは、新しいホストにメモリが要れば、古い順にすぐ止める。止められるホストが無く、メモリも足りなければ、新しいホストの起動を待たせる（チップは「queued · waiting for memory」）。cap を超えたトラックは planned のまま列で待ち、見出しは「queued · 12th」になる。Planner の台詞は「Split it 50 ways; 12 run now, the rest queue.」の形だ（設計書「15. アーキテクチャ」の上限と待ち行列）。
